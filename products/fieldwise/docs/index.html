What Fieldwise Does

Overview

Fieldwise is a Chrome extension built for Salesforce admins, developers, and consultants who work with Field-Level Security every day. It removes the click-through cost of reviewing one Profile or Permission Set at a time and lets you operate on FLS across an entire object, an entire org, or across orgs.

Single-field FLS

View Read/Edit access for every Profile and Permission Set on a chosen field in one table.

Toggle access inline

Stage Read/Edit changes directly on the matrix and apply them through Metadata API.

Snapshots

Save the current FLS state for a field with a label so you can compare or audit later.

Object Audit

Capture every permissionable field on an object in one pass and store it as a single object audit.

Object Compare across orgs

Compare object-level FLS between two saved org states and surface differences.

JSON / CSV / XLSX exports

Export audits for re-import, spreadsheet review, or business-side sign-off.

Local apply history

Every applied change is recorded locally with before/after values and timestamps.

Quick links

Jump to the relevant setup page for any field, Profile, or Permission Set in one click.

Privacy & Data Handling

Privacy

Fieldwise is designed so that your Salesforce metadata and Field-Level Security data never leave the browser-to-org connection.

  • Uses your active browser session with the Salesforce org. No separate Fieldwise account, login, or token is required.
  • Stores no Salesforce credentials. There is no central credential store, no OAuth-to-Fieldwise grant, and no third-party sign-in.
  • Makes API calls directly from the browser to the connected org. There is no Fieldwise proxy server in the middle.
  • Stores snapshots, object audits, and apply history locally in Chrome extension storage on the user's machine.
  • Does not send Salesforce metadata, Field-Level Security data, org identifiers, or credentials to Axiom Gray servers.
✓

Local-only by design. When you clear Chrome extension storage or uninstall Fieldwise, all stored snapshots, audits, and history are removed from your device. Axiom Gray has no copy.

See the privacy summary above before exporting or clearing local browser storage.

Installation

Setup
1
Install from the Chrome Web Store. Add Fieldwise to Chrome. The extension is free and works on any Chromium-based browser that supports Chrome extensions.
2
Pin the toolbar icon. Open the Chrome extensions menu (puzzle icon) and pin Fieldwise so the icon is always visible.
3
Open a Salesforce org. Log in to the org you want to work in. Fieldwise reads from whichever org tab is currently active.
4
Click the Fieldwise toolbar icon. The extension opens. From here you can also click Open in side panel to use Fieldwise alongside your Salesforce tabs without obscuring them.
5
If no org is detected, open or refresh a tab on the target Salesforce org's My Domain URL, then re-open Fieldwise. The extension detects the session from that tab.
i

The side panel mode is the fastest setup for ongoing FLS work — keep one tab pinned to Salesforce Setup and one panel pinned to Fieldwise.

Required Permissions

Access

Fieldwise uses the connected Salesforce user's own permissions. The connected user needs to be able to:

  • Read object and field metadata.
  • Read Profile and Permission Set field permissions.
  • Deploy Profile / Permission Set FLS changes through the Metadata API.

In practice, this means a user with System Administrator or equivalent admin-level access. Read-only users can use the FLS review, Audit, and Compare features but will not be able to apply changes.

!

Apply will fail silently or with an explicit Metadata API error if the connected user does not have permission to modify the targeted Profile or Permission Set. Use a session whose user can deploy to those exact records.

Single Field FLS Review

Workflow

The fastest way to answer "who can see or edit this field?"

1
Open FLS from the main navigation.
2
Choose an object (for example Account, Opportunity, Custom_Object__c).
3
Choose a field. Fieldwise loads the full Profile and Permission Set table for that field.
4
Review each row — Read and Edit columns show the current state for every Profile and Permission Set.
5
Use the search and filter controls to narrow to Profiles only, Permission Sets only, or by name.
6
Use the quick link next to any row to open that Profile or Permission Set in Salesforce Setup.
7
Save the current state as a snapshot for later review or comparison.

Read / Edit semantics

  • Edit implies Read. If you turn Edit on, Read is automatically enabled.
  • Turning Read off removes Edit. A row cannot have Edit without Read.
  • Rows are matched by Profile / Permission Set API name, not by Salesforce record ID. This is what makes the same row meaningful when comparing across orgs.

Security Score

Signal

Each loaded field is given an A-F exposure score based on how broadly Read and Edit are granted across Profiles and Permission Sets.

A
Low exposure risk.
B
Limited or controlled access.
C
Moderate exposure.
D
Broad access that should be reviewed.
F
Very broad access or high review priority.
!

The score is an exposure signal, not a compliance certification. Treat low grades on sensitive fields (SSN, salary, contract value, credit card metadata, regulated PII) as a prompt to review — not as proof of a violation.

Applying FLS Changes

Deploy
1
Stage toggles by switching Read or Edit on any row. Changed cells show a pending indicator.
2
Open Review & Apply. Fieldwise summarizes every pending change.
3
Confirm. The extension deploys the change set through the Metadata API on the connected user's behalf.
4
Fieldwise refreshes the table from the org so the live state matches what you just applied.
5
The apply is recorded in History with before / after values and a timestamp.
i

Fieldwise deploys only the specific field permission entries that changed. It does not push the whole Profile or Permission Set — unrelated permissions are not overwritten.

Multi-Field Editing

Workflow

Use the multi-field workflow when you need to update the same set of Profiles or Permission Sets across several fields on the same object.

1
Choose an object.
2
Select multiple fields. Each selected field shows as a chip at the top of the workspace.
3
Load selected fields. Fieldwise fetches the current FLS state for all chosen fields.
4
Pick an active field from the chip row. The table shows the Profiles and Permission Sets for that field.
5
Search Profiles and Permission Sets and toggle Read / Edit.
6
Move between selected fields by clicking another chip. Pending changes are preserved per field.
7
Open Review pending changes. The summary groups changes by field.
8
Apply. Fieldwise deploys all pending changes in a single Metadata API call and records them as one grouped History entry.

Key terms

  • Selected chips — the fields you have loaded into the multi-field workspace.
  • Active field — the chip currently being edited. Its Profile / Permission Set rows are shown below.
  • Pending indicator — a small marker on a chip when that field has unapplied changes.
  • Clear all — removes all selected fields and discards pending changes after confirmation.
  • Discard — drops pending changes on the active field without removing it from the workspace.

Object Audit

Audit

Object Audit captures FLS for every permissionable field on an object — useful for compliance reviews, pre-release audits, and cross-org comparisons.

1
Open Audit from the main navigation.
2
Select the object.
3
Run Capture All Fields. Fieldwise loops over every permissionable field on the object and collects the Profile / Permission Set state.
4
Review the field count and any skipped non-permissionable fields.
5
Save the result as a set of field snapshots tied to this object audit.
6
Export using one of the three formats below.
FormatUse it for
JSONRe-import back into Fieldwise. Required for Object Compare across orgs.
CSVQuick spreadsheet review. Easy to grep, diff, and paste into tickets.
XLSXBusiness-side review with pivot tables, conditional formatting, and shareable workbooks.
i

JSON is best for Fieldwise import and Compare. CSV is best for quick review. XLSX is best for pivot-style business review.

Snapshots

Saved State

A snapshot is a saved FLS state for a single field on a specific object at a specific time. Object audits create many field snapshots together in one batch.

Each snapshot carries:

  • Label — a free-text name you give the snapshot.
  • Org label — the connected org's display name, used to disambiguate when comparing.
  • Captured time — local timestamp of when the snapshot was taken.
  • Object API name — for example Account.
  • Field API name — for example AnnualRevenue.
  • Permissions rows — Read / Edit per Profile and Permission Set, keyed by API name.

Snapshots and object audits can be exported and re-imported as JSON. This is how you carry state between orgs or between team members.

Object Compare Across Orgs

Compare

Object Compare is the workflow for diffing object-level FLS between two orgs — typically Production vs Sandbox before a release, or two client orgs during a migration.

Full workflow

1
Open Org A in Chrome.
2
Go to Audit.
3
Select an object, for example Account.
4
Click Capture All Fields.
5
Save the audit in Fieldwise.
6
Open Org B in the same Chrome profile.
7
Capture and save the same object.
8
Go to Snaps.
9
Open Object Compare.
10
Pick the Baseline org.
11
Pick the Compare with org.
12
Pick the object.
13
Click Compare Object.
14
Review matching, different, missing, and new fields.
15
Use filters to focus on the permissions that matter.
16
Expand any field to see exact Profile and Permission Set Read/Edit differences. Export CSV only when you need to share findings outside Fieldwise.
✓

This replaces hours of manual Profile and Permission Set checking across environments. The selected orgs and object should be visible at a glance, matching results should stay out of the way when possible, and the interface should prioritize differences and review actions.

!

Object Compare is review-focused in this version. It does not auto-apply differences to the target org. Treat the comparison output as a change list to plan and apply intentionally.

History

Audit Trail

The History section records every successful FLS apply Fieldwise has made on this device.

Each entry includes:

  • Time of the apply.
  • Org label and connected user details where available.
  • Source / target field (object API name and field API name).
  • Before and after Read / Edit values for every changed Profile or Permission Set row.
  • Grouping for multi-field applies — a single Review & Apply produces one grouped entry, not one per field.
i

History is stored locally. Default retention is 500 entries. The oldest entries are removed first once the limit is exceeded. Configure retention in Settings / Config.

Theme & Visual Modes

Display

Fieldwise uses a focused product visual system: dark graphite surfaces, CRM-blue selected states, teal connected states, amber review states, and rose destructive or error states.

Themes are meant to improve readability and comfort, especially during longer FLS review sessions. Changing the workspace theme does not change Salesforce data, saved snapshots, audit history, or export formats.

i

Quick Links

Navigation

Fieldwise shows small "↗" quick-link controls next to fields, Profiles, and Permission Sets wherever they appear. Clicking a quick link opens the relevant setup page in a new browser tab so an admin can verify the live record without leaving the workflow.

i

Quick links are session-routed — they open in the same Salesforce org the active tab is connected to. If you do not see a quick link for a row, that record's setup URL was not derivable from the available metadata.

Troubleshooting

Fix It
No Salesforce session detected
Open or refresh a Salesforce tab on the target org's My Domain URL, then re-open Fieldwise. The extension reads the session from an active org tab.
Object list does not load
Confirm the connected user has metadata read access for the org. Check the configured API Version in Config because an unsupported version can return an empty list.
Field list does not load
Make sure the object is selected and the user can read field metadata for that object. For very large objects, allow the metadata fetch a few extra seconds before refreshing.
Field is not permissionable
System fields, formula fields, master-detail fields, and some managed package fields are not controlled by Field-Level Security. Fieldwise marks these as not permissionable and skips them during apply.
Metadata API apply failed
The connected user may lack deploy permission, the target Profile or Permission Set may be locked, or Salesforce may have rejected the deploy. Re-open Review & Apply and read the exact Metadata API error message.
Object Compare shows no shared objects
The two captures may not contain the same object API name, or one side may not have been saved as an object audit. Re-capture the same object in both orgs, label the orgs clearly, and run Compare again.
Imported JSON says invalid format
Confirm the file came from a Fieldwise JSON export and has not been hand-edited, truncated, or converted by another tool. CSV and XLSX exports are for review; JSON is for Fieldwise import and Object Compare.
Profiles or Permission Sets appear missing in target
Compare matches by Profile or Permission Set API name, not Salesforce record ID. If a Profile was renamed or replaced in the target org, it can appear as missing even when a similar label exists.
History entries disappeared after retention limit
Retention pruning removes oldest entries first. Raise History Retention in Config if your team needs a longer local audit window.
Snapshots are missing because Chrome storage was cleared
Snapshots, object audits, and history live in Chrome extension storage. If that storage was cleared, the Chrome profile was reset, or Fieldwise was uninstalled, local records are removed. Re-import from saved JSON exports where available.

FAQ

FAQ
Does Fieldwise store Salesforce credentials?
No. Fieldwise uses the active browser session in the Salesforce tab. It does not store Salesforce usernames, passwords, session credentials, or a separate Fieldwise login.
Does Axiom Gray receive my Salesforce data?
No. Fieldwise does not send Salesforce metadata, FLS data, org identifiers, snapshots, audit exports, or credentials to Axiom Gray servers.
Can Fieldwise compare Production and Sandbox?
Yes. Capture and save the same object in each org, then use Object Compare in Snaps. Label the orgs clearly so Production, Sandbox, UAT, and Dev are easy to distinguish.
Can Fieldwise update both Profiles and Permission Sets?
Yes, when the connected Salesforce user has permission to deploy those field permission changes through the Metadata API.
What API does Fieldwise use?
Fieldwise reads metadata and field permissions through Salesforce APIs and applies selected FLS updates through the Salesforce Metadata API.
Can Fieldwise modify managed package fields?
Only where Salesforce allows those permissions to be modified. Locked managed package metadata or non-permissionable fields may be viewable but not editable.
Does Object Compare apply changes automatically?
No. Object Compare is review-focused. It identifies matching, different, missing, and new field permission states so admins can decide what to apply intentionally.
Can I use Fieldwise without leaving Salesforce?
Yes. Fieldwise opens from the Chrome toolbar and can run as a side panel next to Salesforce, so admins can review FLS and open setup quick links without losing context.
What happens if Chrome storage is cleared?
Local snapshots, object audits, and history can be lost. Export object audit JSON before major releases or reviews if you need a portable backup.
Is data synced to a backend anywhere?
No. Fieldwise stores working data locally in Chrome extension storage and talks directly to the connected Salesforce org from the browser.
Is the A-F score a compliance guarantee?
No. It is an exposure signal to help prioritize review, not a certification or legal compliance result.

Best Practices

Recommended
  • Label orgs clearly in Config so Production, Sandbox, UAT, and Dev are unambiguous in compare dropdowns and history rows.
  • Export an object audit JSON before major releases for every object whose FLS could be touched — this is your point-in-time evidence.
  • Compare Sandbox vs Production before deployment windows. Catch drift before it ships.
  • Review F-rated sensitive fields first. The score exists to help you prioritize attention.
  • Keep history retention high enough for the audit window your team needs. Raise the limit in Config if 500 entries is not enough.
  • Use CSV / XLSX exports for team review. JSON is for tools; CSV and XLSX are for humans and stakeholders.
  • Re-capture after applying changes so your next compare uses the new ground truth.
